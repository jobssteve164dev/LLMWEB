# 统一训练环境发行与分发

状态：第一阶段实施基线

更新日期：2026-08-15

## 1. 要解决的用户动作

用户只需要完成一个动作：连接一台自己控制的电脑。LLMWEB 负责识别能力、取得正确环境、验证可用性并保持连接。用户不需要理解容器、CUDA、MPS、下载代理或训练框架。

CloudMCP 管理的 GitOps 节点与外部用户电脑必须消费同一个训练环境版本和相同内容摘要。GitOps 节点通过既有 Release 产物代理下载安装包，外部用户通过 LLMWEB 产品域下载同一发行内容；两种入口只允许在下载传输和系统服务托管方式上不同，不能形成两套训练环境。

## 2. 统一对象

统一训练环境是一个不可变发行版，不是强行包含所有平台的单个物理镜像。发行版可以按平台提供多个变体，但每个变体必须是节点一次下载、一次校验、一次执行的自包含包；服务端发行索引只负责选择变体，不能变成节点继续下载内部资产的第二份合同。每个包由一个绑定源码 revision 的摘要与签名定义，并内含完成安装所需的全部固定内容：

- 环境版本、包格式版本、平台和源码 revision。
- 固定安装入口、Runner 二进制、训练运行时以及它们的内部内容摘要。
- Linux CPU/NVIDIA 变体的标准 Docker archive、固定运行镜像引用、驱动兼容要求和功能自检。
- Apple Silicon 变体的原生环境、最低 macOS 要求和功能自检。
- 固定训练引擎、源码 revision、数据素材和许可证证据。
- SBOM、漏洞报告、最低资源和自检命令。

同一版本的任何包字节、摘要、签名或选择规则不得被覆盖。Docker daemon 导入归档后产生的本地 image ID 受镜像存储后端影响，不属于发行身份；运行时以包摘要/签名、包内内容摘要、固定镜像引用、导入内容检查和功能自检共同验收。需要改变内容时发布新版本。

## 3. 第一阶段范围

第一阶段正式交付 Linux x86_64 CPU 入门训练变体：

- 预构建 `nanoGPT` CPU 容器，节点不再执行 `docker build`。
- 预构建 Linux amd64 Runner。
- 包含固定安装入口、Runner、CPU 镜像归档、元数据和自检的单个 Linux amd64 自包含包。
- 由 LLMWEB 产品域提供的 Artifact Gateway。
- 外部连接命令与 CloudMCP/GitOps 入池消费相同包字节；GitOps 只改变传输代理。
- 至少 4 核、8GB 内存和 20GB 可用磁盘的安装前检查。
- 已绑定节点拒绝用另一个配对码静默改绑。
- 包下载、摘要与签名验证、安全解包、`docker load`、导入内容检查和最小运行自检全部通过后，Runner 才注册为可用。

Linux NVIDIA 和 Apple Silicon 在同一清单协议中保留明确变体，但在对应预构建产物和真实硬件验收完成前不得标记为可用，也不得改写现有稳定路径冒充闭环。

## 4. 分发路径

```text
外部用户连接指令 ───────────────┐
                              ▼
                        LLMWEB 产品域
                          发行包索引
                              │
                              ▼
                       Artifact Gateway
                              │
                        包 SHA256 / 签名
                              │
                              ▼
                    单个自包含平台包 / 本地缓存

CloudMCP → GitOps Runner Target
            → 既有 /gh-release 代理 ─┘
```

Artifact Gateway 只允许代理当前不可变发行索引列出的平台包，不接受任意上游 URL。它必须保留 `Range`、`Content-Range`、`ETag` 和内容长度，以便大文件断点续传。客户端即使通过不同代理或缓存取得包，也必须验证同一包摘要与签名。

GitOps 内部节点不另建 LLMWEB 下载协议：控制面在一次 `model-training` Runner 动作安装开始时解析 LLMWEB 当前可信正式发行，校验不可变标签、源码 revision、平台包名、包 SHA256 和签名，再把这一份包的确切发行身份固化到该 Runner Action 和本次 Operation。随后仅为该包创建一次已有 Agent 制品路径的受治理授权；Runner Target 上的 Agent 复用既有校验下载器取得该包，验证后执行包内固定入口。调用方不能传 Release 地址、标签、资产名或摘要；安装开始后即使出现新发行，也不得改变已在执行的 Operation。

“复用既有路径”要求生产者、包封装、摘要/签名、发布入口、代理授权、Agent 下载器、固定入口和终态回报逐段一致。只复用 `/gh-release` URL、却为 manifest、Runner、宿主 runtime 或镜像分别生成授权和下载流程，属于平行私有合同，禁止实现。

训练环境版本属于 Runner Action 的已解析发布身份，不属于 GitOps 运行时代码或公共契约。GitOps 代码只实现稳定的 `model-training` 动作、可信正式发行解析和既有 `/gh-release` 分发能力；LLMWEB 发布新版本不要求修改或重新发布 GitOps 运行时代码。只有发行清单协议、信任来源或稳定 Runner 动作语义本身改变时，才进入跨系统契约变更。

这里的 Runner Target 是绑定现有 Agent 节点的范围与资源边界，不要求 Server 凭证。发行包安装的是该范围内的 `model-training` Runner 动作；Target、Runner 动作、一次安装 Operation 和最终服务/容器证据必须分别记录，不能用产品命名的容器或安装任务代替 Target。

首次安装缺少完整且校验通过的包时不得退回 GitHub、PyPI 或模型站点随机下载，也不得由包内安装器继续拉取执行资产。升级时如果本机已缓存同一包摘要/签名、导入内容检查和最小运行自检均通过，必须原位复用，不得为了重新绑定 Runner 动作而重复加载同一运行时；任一验证不成立才重新取得并校验整包。已经校验的本地缓存可以在网关暂时不可用时继续运行已有环境。

## 5. 节点归属

第一阶段一台 Runner 节点同一时间只归属一个 LLMWEB 工作区。环境缓存可以复用，以下内容不得跨工作区复用：

- Runner 设备身份。
- 原始数据与授权预览。
- checkpoint 与模型产物。
- 业务训练日志。
- 用户存储凭证。

安装器发现已有 Runner 身份时，必须使用设备凭证和新配对码向控制面确认两者属于同一工作区；同一工作区可以保留身份、数据与产物完成环境升级，工作区不同则停止并提示正式解除原连接。不得忽略新配对码继续旧身份，也不得静默覆盖旧身份。

节点转移的正式顺序是：确认无运行任务、保留或导出产物、撤销旧设备身份、清除精确身份状态、保留校验通过的共享环境缓存、使用新配对码注册并验证工作区隔离。节点恢复出厂不是常规转移方案。

## 6. 宿主机与环境责任

宿主机负责 Docker、NVIDIA 驱动、Metal、磁盘、文件权限、出站网络和系统服务。训练环境负责训练框架、Python 用户态依赖、固定训练逻辑和自检。

容器不能携带 NVIDIA 内核驱动；Apple MPS 不能以 Linux Docker 镜像交付。因此统一清单必须维护平台兼容矩阵，能力不满足时在大文件下载前失败并给出用户可行动说明。

## 7. 连接状态

内部状态按以下顺序推进：

```text
已取得配对码
→ 正在检查电脑
→ 正在下载训练环境
→ 正在验证训练环境
→ 正在连接
→ 可以训练
```

只有 Runner 身份有效、能力与磁盘满足、包摘要与签名正确、导入内容和固定镜像引用正确、最小自检通过、数据和输出目录可读写、Runner 心跳正常时，网页才显示“算力已连接”。

## 8. 任务协议

训练任务引用统一环境版本和后端，而不是由用户或控制面自由拼接镜像：

```json
{
  "environment": {
    "version": "1.0.0",
    "backend": "linux-amd64-cpu"
  }
}
```

Runner 只接受自身安装并验证过的环境版本、固定后端和批准镜像。训练开始后环境版本保持不变；新任务可以使用新的稳定版本，旧版本在回滚期内保留。

## 9. 存储与并发

存储分为三个边界：只读且按摘要复用的环境缓存、严格归属工作区的数据、严格归属实验的训练产物。第一阶段每个 Runner 同时只执行一个任务。

清理环境缓存不得删除仍在使用的镜像或用户产物。成功安装、失败、取消和升级都必须报告安装阶段并只清理本次下载的临时文件。

## 10. 供应链与验收

每个正式发行版必须具备：固定源码 revision、平台包 SHA256 与签名、包内内容摘要、固定运行镜像引用、构建来源、SBOM、完整漏洞报告和不可变发布标签。已有修复但发行物尚未采用修复的 High/Critical 漏洞必须阻断发布；暂时没有上游修复的漏洞必须保留在报告中，并在后续发行重新评估，不能静默忽略。只有经过代码可达性或上游修复证据审计、限定精确漏洞与包、写明失效条件和最晚复核日期的例外，才能从阻断集合中移除。

第一阶段闭环要求：

1. CI 从干净源码构建 Runner、标准 Docker archive 和自包含平台包；构建 Job 只产生候选包。独立验证 Job 必须重新下载完全相同的候选包，使用真实安装消费者校验包摘要/签名、安全解包、实际 `docker load`、固定镜像引用、内容检查与 PyTorch 最小自检。发布 Job 只能发布已经通过验证的同一包字节，不能重新构建或替换文件。
2. 消费者矩阵必须覆盖正式支持的归档解释器、Docker 镜像存储后端、平台和架构。构建 Job 与验证 Job 使用同一 hosted Docker 后端只能证明内部自洽，不能作为跨节点兼容证据；生产 Target 不能成为首次消费者测试。
3. 最终包不包含 Git、缓存、密钥、工作区状态或用户产物，也不包含会触发后续执行资产下载的动态 URL。
4. 外部用户入口与 GitOps Agent 分别通过 LLMWEB 产品域和既有受治理代理取得同一包字节。
5. 干净 Linux 节点不执行镜像构建、不下载第二份执行资产即可完成安装和自检。
6. CloudMCP/GitOps 与外部连接得到相同版本、包 SHA256、签名和包内内容摘要。
7. 4 核 8GB CPU 节点完成数据准备、训练前基线、训练、checkpoint 选择、同测试集复测和模型导出。
8. 外部用户只看到“连接电脑”和可行动状态，不看到下载代理或后端差异。

## 11. 失败证据与北向观测

安装失败不能只留下“某阶段失败”。安装器必须同时保留两类证据：供节点内部排障使用的有界原始命令输出，以及不含凭证和自由文本的结构化失败码。结构化失败码同时写入 Agent 捕获的标准错误流和节点状态文件，避免进程退出、控制面重启或日志截断后丢失根因。

GitOps Agent 必须把安装命令的 stdout、stderr 和终态持久化；日志达到上限时保留尾部，因为安装器在退出前写入最终失败码。GitOps 控制面从操作日志与节点状态中读取失败证据，按白名单输出 `code`、`stage`、安全摘要、证据来源和“操作日志是否已捕获”，不得把原始日志、配对材料、下载授权或设备凭证返回北向调用方。

CloudMCP 的具名 Runner Action 状态工具必须原样保留上述结构化字段，不自行把它们压缩成通用失败，也不需要理解 LLMWEB 的内部日志格式。完整逻辑验证至少覆盖：安装器分类与落盘、Agent 同时捕获 stdout/stderr 且在有界日志中保留末尾失败码、GitOps 对旧日志和新结构化码的归因与脱敏、CloudMCP 具名工具读回。不能因本地没有容器而跳过这些边界；真实归档的加载和运行验证由发布前的独立 Linux CI 硬门禁承担。
