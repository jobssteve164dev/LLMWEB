# LLMWEB 系统边界

状态：首版架构基线

更新日期：2026-08-03

## 1. 架构目标

LLMWEB 使用网页控制面管理用户动作，使用用户环境中的 Runner 执行数据处理、训练、评测和导出。架构必须同时满足：

- 原始训练数据不离开用户环境。
- 用户 GPU 不需要开放入站端口。
- 控制面断开不终止已接受的训练。
- 不同训练引擎的实现差异不进入用户主流程。
- 控制面不能把 Runner 变成通用远程命令执行入口。

## 2. 系统组成

```text
浏览器
  │
  ▼
Web 工作台 ── 控制面 API ── PostgreSQL
                    │
                    ├── 平台对象存储（可选元数据附件）
                    │
              出站 HTTPS / 事件流
                    │
                    ▼
              用户 GPU Runner
                    │
          ┌─────────┼─────────┐
          ▼         ▼         ▼
       数据处理   训练容器   评测/导出
                    │
                    ▼
          用户本地目录或用户 S3
```

### 2.1 Web 工作台

负责项目、数据、算力、训练、评测和模型的用户界面。Web 只与控制面通信，不直接连接 Runner。

### 2.2 控制面

负责身份与工作区、Runner 配对、任务定义、任务租约、实验元数据、事件接收和用户可见状态。控制面不持有训练进程，也不把浏览器连接当作任务生命线。

### 2.3 Runner

Runner 是安装在用户 GPU 主机上的受限执行代理。首版使用 Go 实现，负责：

- 使用一次性配对码绑定一个工作区。
- 主动建立出站连接并汇报能力。
- 领取结构化且版本化的任务。
- 启动平台批准的训练容器。
- 本地持久化任务、日志和事件缓冲。
- 采集 GPU 与进程指标。
- 在恢复连接后补传状态。

Runner 不包含 PyTorch 或训练框架。Python、CUDA 用户态依赖和训练逻辑位于版本固定的容器镜像中。

### 2.4 执行容器

首版训练引擎为 LLaMA-Factory。数据处理、训练、评测和导出可以使用不同镜像，但必须消费统一任务协议并产生统一事件格式。

## 3. 首版技术栈

| 责任 | 技术 |
|---|---|
| Web 工作台 | Next.js、React、TypeScript |
| 控制面 API | FastAPI、Pydantic |
| 元数据 | PostgreSQL |
| 平台文件接口 | S3 兼容对象存储 |
| Runner | Go、Docker Engine API |
| 数据处理 | Python、Polars、PyArrow、Hugging Face Datasets |
| 训练 | LLaMA-Factory |
| 评测 | EvalScope 与任务专用评测器 |
| 通信 | HTTPS；日志和指标使用 WebSocket 或 SSE 推送至浏览器 |
| GPU 观测 | NVML 与 `nvidia-smi` |

首版采用模块化单体控制面。Runner 通过 PostgreSQL 支撑的任务租约 API 主动领取任务，不以 Celery Worker 方式暴露在用户网络中。规模证明需要后，再引入独立消息系统。

## 4. 数据主权

### 4.1 不进入控制面的内容

- 原始训练、验证和测试数据。
- 未经用户授权的样本内容。
- 模型权重和 checkpoint 文件。
- 用户本地完整路径结构。
- Hugging Face、ModelScope、S3 等长期访问密钥。

### 4.2 控制面允许保存的内容

- 数据集名称、版本、哈希和来源类型。
- 行数、Token 分布、异常数量等统计结果。
- 用户明确授权的少量预览样本。
- 训练配置、实验指标和模型版本元数据。
- 产物所在的受控引用，不默认复制产物。

### 4.3 数据处理位置

所有读取原始数据的操作在 Runner 或其启动的数据处理容器中执行。控制面发送处理意图，Runner 返回统计结果和用户授权内容。

## 5. 任务协议

控制面只能下发版本化、可校验的任务，不能下发任意 Shell 字符串。首版任务描述至少包含：

- 任务协议版本与任务 ID。
- 工作区和项目标识。
- 数据版本引用。
- 基础模型及精确 revision。
- SFT、LoRA 或 QLoRA 方案。
- 资源限制和预期输出。
- 训练镜像的精确版本。

协议初始结构位于 `contracts/training-job.schema.json`。协议变化必须保持版本可识别，Runner 遇到不支持的版本时明确拒绝任务，不得猜测执行。

## 6. 任务生命期

- Runner 领取任务并完成本地持久化后，才向控制面确认接受。
- 接受后，Runner 成为执行状态的权威来源。
- 浏览器关闭不影响任务。
- 控制面断开时，Runner 继续训练并缓冲事件。
- Runner 离线时，控制面显示“状态待同步”，不得擅自标记失败。
- 用户暂停时，Runner 在安全 checkpoint 边界暂停。
- 用户取消时，Runner 先请求训练进程保存，再终止并报告实际保留产物。
- 主机重启后，Runner 根据本地任务记录提供恢复或明确失败原因。

## 7. 安全边界

首版必须满足：

- 一个 Runner 只绑定一个工作区。
- 配对码一次有效、短时有效，交换为可撤销的设备凭证。
- Runner 只接受所属工作区、支持协议版本的任务。
- 只运行平台批准、内容固定的镜像。
- 数据和输出目录使用显式允许列表。
- 默认禁止任意用户脚本、远程 Shell 和不受控的模型远程代码。
- 凭证不进入任务 JSON、命令行、日志或模型产物。
- 训练容器不得获得控制面设备凭证。
- 日志和事件上报前进行密钥与环境变量脱敏。

模型许可证、数据许可证和受限模型授权属于每个实验必须记录的来源信息，但平台不能替用户推定其拥有使用权。

## 8. 存储边界

### 控制面 PostgreSQL

保存用户、工作区、项目、Runner、数据版本元数据、任务、实验、指标摘要和模型记录。

### Runner 本地状态

保存已接受任务、事件缓冲、容器引用、checkpoint 引用和恢复信息。该状态必须能在 Runner 进程或主机重启后重新读取。

### 用户产物存储

模型、checkpoint 和原始数据默认保存在用户本地目录或用户指定的 S3 兼容存储。平台不得因为任务结束自动删除用户产物。

## 9. 仓库职责

```text
apps/web/
  用户操作界面和 Web 健康入口

services/control-plane/
  控制面 API、领域规则和持久化入口

runner/
  设备配对、能力检测、任务领取和本地执行监管

contracts/
  控制面与 Runner 共用的版本化 JSON Schema

docs/product/
  产品目标、用户动作、功能范围和成功标准

docs/architecture/
  数据、执行、通信、安全和技术责任边界
```

## 10. 演进约束

后续可以增加其他 GPU 平台、训练引擎、多机训练或生产部署，但必须遵守：

- 新能力通过同一任务与用户动作模型接入。
- 不因引擎或供应商差异增加一套用户必须理解的主流程。
- 不改变“原始训练数据默认且必须留在用户环境”的立项约束，除非用户主动选择另一个独立产品模式。
- 不能用更早失败、静默降级或丢弃任务替代真实的断线恢复与结果交付。
